# DecisionSpec

DecisionSpec is a language-agnostic, **spec-driven compliance** CLI. A project
writes its architectural decisions and behavior specs in a small DSL
(`.spec` files, committed to git). DecisionSpec compiles them into diagrams
(Mermaid + PlantUML) and per-layer test artifacts (pytest, Gherkin,
Playwright, Rego/conftest, import-linter, dependency-cruiser), then runs a
**compliance gate** that produces a traceability matrix
(decision → requirement → test → result) and fails the build if anything is
uncovered or failing.

Think *Structurizr + Cucumber + ArchUnit + OPA, glued by one compiler and one
gate*. DecisionSpec is an external binary; your project never depends on it as a
library.

Status: **MVP** (see [MVP limitations](#mvp-limitations)).

## Quickstart

```sh
# build the workspace (Rust 1.98+, edition 2024)
cargo build

# start a demo project
mkdir my-project && cd my-project
/path/to/decispec init --demo
decispec check        # parse + validate all specs/**/*.spec
decispec gen          # emit diagrams + test artifacts
decispec gate         # red: --demo glue stubs raise NotImplementedError
                      # (plain `init` ships an empty glue package, so the
                      # generated tests fail with AttributeError instead —
                      # same red gate, different error shape)
# ... implement tests/glue/__init__.py ...
decispec gate         # green
decispec query AUTH-001
```

Already-started project? Bootstrap a draft spec from the directory layout
and import graph instead of writing the model from scratch:

```sh
cd my-existing-project
decispec init          # once: decispec.toml, specs/, tests/glue/
decispec extract       # writes specs/extracted.spec (or: extract --stdout)
# review + rename the draft, then add decisions + requirements
decispec check && decispec gen
```

## The workflow

1. **Spec first.** Write decisions (`decision`), the system model
   (`model`: containers, relationships, flows) and behavior specs (`spec`)
   in `specs/*.spec`. `decispec check` enforces ID uniqueness and
   cross-references with `file:line` errors.
2. **Generate.** `decispec gen` renders `docs/diagrams/*.mmd|*.puml` and
   test skeletons under `tests/generated/<layer>/`. Everything generated
   carries a `GENERATED BY DECISIONSPEC — DO NOT EDIT` header; regeneration is
   byte-identical, never touches `tests/glue/`, and removes stale artifacts
   whose spec item disappeared.
3. **Implement the glue.** Generated tests call into your code through the
   glue package (`tests/glue`, configurable via `decispec.toml`
   `[stack] glue_module`). The glue is the only hand-written test code.
4. **Gate.** `decispec gate` runs the available toolchains (or consumes
   `--results <dir>`), matches JUnit results back to spec items by test
   name, and renders the matrix. Exit 0 = compliant, 1 = gate violation, 2
   = DecisionSpec could not run the gate at all (unparseable specs, bad CLI
   usage, missing results dir, I/O errors). See [Exit codes](#exit-codes).

## The DSL

Files are UTF-8, `#` starts a line comment, multiple files merge into one IR.
IDs match `[A-Za-z0-9_-]+` and must be unique across the workspace.

```sdl
decision AUTH-001 "Use OAuth2 client credentials for service-to-service auth" {
  status: accepted                # accepted | proposed | rejected | superseded
  context: "Internal services need machine-to-machine auth without shared secrets"
  consequences: "+ no shared secrets in code; - token latency on cold start"
  superseded_by: AUTH-007        # only when status: superseded
}

model {
  container api "Orders API"
  container auth "Auth Service"
  rel api -> auth: "requests token"
  flow svc_auth {
    api -> auth: "POST /token"          # sync message
    alt valid {
      auth --> api: "200 + access token" # dashed / return message
    } else {
      auth --> api: "401 unauthorized"
    }
  }
}

spec AUTH-001 {                     # must reference an existing decision ID
  requirement AUTH-001-R1 (EARS) {
    text: "WHEN a service presents valid client credentials THEN the auth service SHALL return an access token"
    layers: [unit, contract, e2e]   # unit | contract | e2e | infra | fitness
    scenarios: [valid_token]        # scenario IDs from this spec block
  }
  scenario valid_token {
    given: "valid client credentials"
    when: "a token request is made"
    then: "the response status is 200 and a token is returned"
  }
  invariant token_ttl {
    expr: "access_token.ttl_seconds <= 3600"
    layers: [unit]
  }
  infra_policy no_hardcoded_secrets {
    description: "No secrets committed in source or config"
    layers: [infra]
  }
}
```

Semantics:

- `status: accepted | proposed | rejected | superseded` (default `proposed`).
  Accepted/proposed decisions must have requirements; rejected decisions are
  excluded from the gate; superseded decisions are excluded from hard failures
  (warnings + coverage-drift detection instead).
- Layers live on **requirements**; a scenario's layers are the union of the
  layers of every requirement referencing it. Invariants and infra policies
  carry their own layers.
- `flow` bodies contain `a -> b: "label"` (sync), `a --> b: "label"`
  (return) and `alt NAME { ... } else { ... }`; either branch may itself
  contain `alt` blocks, to arbitrary depth.
- Strings are double-quoted (`\"` and `\\` escapes); unterminated strings are
  parse errors.

Writing specs — what makes a decision worth writing, the EARS pattern, a
worked example, and the anti-patterns: see
[docs/SPEC_AUTHORING.md](docs/SPEC_AUTHORING.md).

## Commands

| Command | Behavior |
| --- | --- |
| `decispec init [--demo]` | Write `decispec.toml`, `specs/`, `tests/glue/`, `.decispec/`, `.gitignore` entries. `--demo` adds the AUTH-001 demo spec + glue stubs. |
| `decispec check` | Parse + validate all `specs/**/*.spec`. Errors (duplicate IDs, unknown refs: spec→decision, requirement→scenario, `superseded_by` target, flow participant not declared as container, bad layer/status) print as `file:line: message`. Exit 0 clean, 1 on spec error — reporting malformed specs *is* check's job, so it is a finding (1), not a "cannot run" (2) like `gen`/`gate`. |
| `decispec gen` | Write artifacts under `docs/diagrams/` and `tests/generated/`, print a summary. Idempotent; never touches `tests/glue/`; deletes stale generated files (header present but no longer rendered). Exits 2 if the specs do not parse/validate — codegen needs a loaded workspace. |
| `decispec test` | Run installed toolchains, collect JUnit XML + write `tests/generated/results/manifest.json`. Skipped (toolchain not installed) is **not** a failure; exit 1 only if an executed toolchain failed. |
| `decispec gate [--json] [--results <dir>] [--strict-skipped]` | Build the matrix + verdict. Without `--results` it first runs the adapters; with `--results` it consumes JUnit XML from that dir. `--strict-skipped` escalates `SKIPPED` rows to `FAIL` (see [Gate semantics](#gate-semantics)). Always writes `.decispec/report.json` and records the run in `.decispec/decispec.db`. Exit 0 = verdict PASS, 1 = verdict FAIL **and nothing else** (specs that fail to parse/validate exit 2, since the gate could not be built at all), 2 = could not complete (bad CLI usage, unparseable specs, missing `--results` dir, I/O or engine errors). |
| `decispec query <ID>` | Print the decision subtree (fields, model/flows, requirements/scenarios/invariants/policies with layers + artifact paths, last gate status from the store). Accepts decision, requirement, scenario, invariant and policy IDs. |
| `decispec extract [path] [--stdout]` | Bootstrap a draft spec from an already-started Python/JS/TS project: containers from top-level directories — or from the children of a single umbrella directory that holds the code (`src/`, your main package) — relationships from the import graph, decisions recovered from ADR markdown docs (`docs/adr/`, `docs/decisions/`, `adr/`, `decisions/`) as `decision` blocks with a `# Source:` comment each, plus a suggested `[stack.fitness.packages]` mapping. Writes `specs/extracted.spec` (refuses to overwrite it: exit 2 — delete it or pass `--stdout`) or prints the draft to stdout with `--stdout`. Warnings always go to stderr; the fitness TOML suggestion prints to stdout, or to stderr with `--stdout`. Recovery stops at structure: requirements are never inferred — the draft header says so. Exit 0 on success (warnings included), 2 when the tree has no source files or cannot be analyzed. |
| `decispec index [--out <path>]` | Write a single GitHub-renderable `docs/decisions.md` (default; `--out` overrides) embedding the mermaid architecture/flow diagrams plus decision/requirement/scenario tables — the whole decision picture for anyone browsing the repo. On-demand only (never swept by `gen`). Needs a valid workspace: exit 2 on broken specs. |

All commands run from anywhere inside a project; `decispec.toml` is found by
walking up from cwd.

## Exit codes

One rule: **1 = the operation completed and reported findings; 2 = DecisionSpec
could not complete the operation.** A CI step can therefore treat 1 as "there
is work to do" and 2 as "the run itself is broken".

| Code | Meaning |
| --- | --- |
| 0 | The operation completed and there is nothing to report (e.g. `gate` verdict PASS). |
| 1 | The operation completed **with findings**: `gate` verdict FAIL, `check` found spec errors, `test` had an executed toolchain fail, `query` did not find the ID. |
| 2 | DecisionSpec **could not complete** the operation: bad CLI usage or flags, specs that fail to parse/validate for a command that needs a loaded workspace (`gen`, `gate`), a missing or unreadable results dir, I/O or engine errors. |

Note the deliberate asymmetry: `check` reports malformed specs as findings
(exit 1) because diagnosing specs is its entire job, while `gen` and `gate`
abort on the same specs and exit 2 — they have nothing to work with. Bad CLI
usage (unknown flag, missing argument) also exits 2, so a CI step never
mistakes a typo for a compliance violation. `--help` and `--version` exit 0.

## Codegen mapping

Every generated file starts with
`GENERATED BY DECISIONSPEC v0.1 — DO NOT EDIT. Edit specs/*.spec instead.` in the
comment style of the file type.

| IR element | Artifacts |
| --- | --- |
| `flow` | `docs/diagrams/<flow>.mmd` (Mermaid `sequenceDiagram`, `->` → `->>`, `-->` → `-->>`, `alt/else/end`, nesting preserved) **and** `<flow>.puml` (PlantUML). |
| `model` | `docs/diagrams/model.mmd` flowchart (containers + `rel` edges) **and** `model.puml`. |
| scenario on `unit` | `tests/generated/unit/test_<SPEC>_<scenario>.py`: parametrized pytest calling `glue.<scenario>()`, named `test_scenario_<SPEC>_<scenario>_unit` (ids in test names are sanitized: `-` → `_`). |
| invariant on `unit` | `tests/generated/unit/test_invariant_<SPEC>_<inv>.py`: test docstring embeds the invariant `expr`, body calls `glue.invariant_<inv>()`. |
| `stack.lang = "rust"` | additionally `tests/generated/unit/rust/<spec>.rs` rstest-style `#[test]` skeletons with `todo!()` and a `// glue:` comment. |
| scenario on `contract` | `tests/generated/contract/<spec>.feature`: one Feature (named after the decision title), one Scenario per contract-layer scenario, each Scenario named `<spec_id>_<scenario_id>` so the gate can match it per item. |
| scenario on `e2e` | `tests/generated/e2e/<scenario>.spec.ts` Playwright skeleton, titled `<spec_id> <scenario_id>` so the gate can match it per item. |
| `infra_policy` | `tests/generated/infra/<policy>.rego` (`package decispec.<policy>`, `deny[msg]` TODO body with a realistic example) + `tests/generated/infra/conftest.toml`. |
| `rel a -> b` | `tests/generated/fitness/.importlinter` (forbidden: b must not import a; layers: a may import b) — emitted **only when both `a` and `b` have a `[stack.fitness.packages]` mapping**, since import-linter is python-only; a rel with an unmapped endpoint gets a TODO naming the container to map. **and** `tests/generated/fitness/dependency-cruiser.cjs` (forbids b → a; each path matches the container as one path segment). |

## Gate semantics

Matrix rows are decision → requirement → item (scenario / invariant /
infra_policy) → layer → artifact → result. A row fails when:

- **(a)** an accepted/proposed decision has no requirements;
- **(b)** a requirement has no scenarios;
- **(c)** structural coverage: the item is mapped to a layer for which zero
  artifacts were generated (`tests/generated/<layer>/` is empty);
- **(d)** an executed test mapped to the item failed (JUnit `testcase` names
  are matched against the generated test names, which embed the spec item ID);
- **(e)** missing = uncovered: the item's toolchain ran in this run but its
  generated tests have no JUnit result.

Superseded decisions are excluded from hard failures (listed as warnings; if
tests still map to one, a `coverage drift` warning is emitted). Skipped
toolchains (not installed) are **not** failures by default, so a project with
no toolchains installed still gates PASS.

Pass `--strict-skipped` to close that hole in CI. Every row whose toolchain did
not run then becomes `FAIL` instead of `SKIPPED`, and the detail says so:

```
toolchain not run (pytest); skipped is not a failure; treated as FAIL in strict mode
```

This covers both ways a layer can end up skipped — an adapter that recorded
itself as not installed, and a results directory with no manifest at all — so
the flag cannot be defeated by pointing `--results` somewhere empty. Rows with
no generated artifacts are unaffected: they already fail structurally as
`NO-ARTIFACTS` and are not counted twice. Escalated rows move from `skipped`
to `failed` in the counts, and `report.json` carries a `strict_skipped` boolean
so a CI consumer can tell a strict failure from a genuine test failure.

## decispec.toml

```toml
[project]
name = "my-project"

[stack]
lang = "python"              # python | rust (more later)
glue_module = "tests.glue"   # python glue import path
rust_glue = "tests/glue/rust"

[stack.fitness]
# python package import-linter is rooted at. Omit it and `.importlinter` gets
# a TODO comment instead of a live setting, because an empty `root_package`
# would make import-linter reject the file.
root_package = "myapp"

[stack.fitness.packages]
# container-id -> importable python module, so a model container named `api`
# is checked as `myapp.api` rather than a bare `api` no interpreter can import.
# A `rel` is enforced only when BOTH of its containers are mapped here (import-
# linter is python-only); otherwise the generated `.importlinter` carries a TODO
# naming the container to add, and no contract.
api = "myapp.api"
auth = "myapp.auth"

[runners]
# optional per-tool overrides; built-in defaults otherwise. One flat key per
# tool, value = the command to run (split on whitespace: first token is the
# program — a root-relative path works — the rest are fixed prefix args the
# layer-specific args append to):
#   pytest             = "backend/.venv/bin/python -m pytest"
#   playwright         = "npx --no-install playwright"
#   cucumber / karate  = program name checked on PATH
#   conftest           = program name checked on PATH
#   import-linter      = program name checked on PATH
#   dependency-cruiser = program name checked on PATH
# A missing or failing tool is SKIPPED, never fatal: `decispec test` always
# completes and writes the manifest.
```

## Using with AI agents (MCP)

`decispec mcp` serves an MCP server over stdio (newline-delimited JSON-RPC
2.0) so AI agents can call typed tools instead of parsing CLI output — built
for porting projects into DecisionSpec. Configure it in your agent's MCP
config:

```json
{"mcpServers": {"decispec": {"command": "decispec", "args": ["mcp"]}}}
```

The server resolves the project root from its working directory at
`initialize` (walking up for `decispec.toml`), so point the agent's `cwd` at
the project you are porting; every tool also accepts an optional `path`
argument to override the root per call.

| Tool | Returns |
| --- | --- |
| `project_info` | Project root, config (name, stack lang, glue module, fitness packages), and spec/generated file counts. |
| `extract_project` | A bootstrap analysis of an existing Python/JS/TS project: containers, import-graph relationships, ADR decisions, plus the rendered draft spec and fitness TOML. |
| `validate_spec` | `file:line` diagnostics for one `.spec` text without touching the filesystem — the iterate-before-you-write tool. |
| `check_workspace` | Diagnostics and counts for every `specs/**/*.spec` file (structured `decispec check`). |
| `workspace_overview` | The porting work queue: decisions with requirements/layers/scenarios, plus gaps (accepted/proposed decisions without requirements, requirements without scenarios, superseded self-references). |
| `gate_status` | The last gate's verdict, counts, and failing/uncovered/skipped rows from `.decispec/report.json`, or an explicit "no report yet" result. |

Two things the table doesn't tell you, learned from a real agent port
(dogfood, 2026-10-01):

- **Schemas live in `tools/list`.** The table is a summary; call
  `tools/list` for each tool's full input schema (an agent guessed
  `validate_spec` took `{"spec": …}` — it takes `{"text": …}`).
- **Results are JSON inside the MCP envelope.** A `tools/call` reply wraps
  the payload as `content: [{type: "text", text: "<json string>"}]` — the
  `text` field needs a second `json.loads`. Failures carry `isError: true`.

`validate_spec` reports diagnostics phase-by-phase: a text with both a parse
error and a cross-reference error shows only the parse error. Fix, re-send,
repeat until `valid: true` — the first clean answer after one fix can still
hide a second problem behind it.

## Architecture

See [ARCHITECTURE.md](ARCHITECTURE.md) for the pattern diagram and notes.

Cargo workspace; the binary depends on the libraries, nothing depends on the
binary.

```
crates/
  ir/        decispec-ir       typed IR of a whole workspace of specs
                               (+ shared deterministic test-naming helpers)
  parse/     decispec-parse    hand-written recursive-descent .spec parser -> IR,
                               cross-reference validation (file:line diagnostics)
  codegen/   decispec-codegen  IR -> diagrams + per-layer test artifacts
                               (one pure fn per artifact type, all &Workspace -> Vec<GeneratedFile>)
  extract/   decispec-extract  bootstrap a draft spec from an existing
                               Python/JS/TS project (layout + import graph
                               + ADR docs -> decision blocks)
  gate/      decispec-gate     JUnit XML (roxmltree) + run manifest -> traceability
                               matrix + verdict (pure, filesystem-in/report-out)
  store/     decispec-store    rusqlite run history (.decispec/decispec.db)
  cli/       decispec          clap binary; re-exports the libraries
```

Data flow: `.spec` files → `parse` → `Workspace` (IR) → `codegen` renders
artifacts; `gate` consumes IR + JUnit results → `GateReport` (console,
`.decispec/report.json`) → `store` persists runs; `query` reads IR + store.

Dependencies are deliberately minimal: `clap`, `thiserror`, `serde` +
`serde_json`, `roxmltree`, `rusqlite(bundled)`.

## MVP limitations

- **No contradiction checking** between specs/decisions (e.g. overlapping or
  mutually exclusive requirements are not detected).
- **No drift detection** against real infrastructure: `infra_policy` emits
  Rego skeletons; DecisionSpec does not diff them against live Terraform/cloud
  state.
- **Skipped toolchains are silent passes by default.** A layer whose toolchain
  is not installed reports `SKIPPED`, never `FAIL`. The gate only sees what the
  adapters produce. Use `--strict-skipped` in CI to make that a failure.
- **Contract/e2e matching is precise but degrades to suite level.** Unit,
  contract and e2e rows map JUnit test names to individual spec items precisely:
  a broken scenario fails only its own row, and a scenario with no result at
  all is `UNCOVERED`. If no JUnit name in a layer's results matches the id
  DecisionSpec generated (an older `.feature`, a hand-edited test, or a toolchain
  whose naming differs), that row falls back to suite-level judgment and the
  gate prints a `WARNING` naming the item, so green projects do not turn red
  for unrelated reasons. Only the case `name` is probed for that check, never
  the `classname`: cucumber reports the feature file path there, which contains
  the spec id even when the scenario titles predate the generated naming.
- **Infra/fitness rows are adapter-status-based.** They are judged from adapter
  exit status, not parsed violations, since those toolchains emit no JUnit.
- **Fitness artifacts are best-effort skeletons.** `.importlinter` module paths
  come from `[stack.fitness.packages]` (see above) and a contract is emitted only
  for a rel whose both containers are mapped; `dependency-cruiser.cjs` paths are
  the container ids as path segments (`(^|/)api(/|\.|$)`), which is correct for a
  JS/TS tree where a container is a directory but wrong if your JS layout differs.
  Both tools were executed against these artifacts on fixture trees
  (import-linter 2.5.2, dependency-cruiser 18.5.0) — see the fitness notes above
  for the exact contract spelling and regex rules they require.
- **Contract/e2e reporter naming is an assumption.** The generated contract and
  e2e test names were chosen to survive JUnit round-tripping, but neither
  cucumber/karate nor playwright is available in this repo, so the exact
  testcase names those reporters emit are unverified. If they disagree, the
  gate silently degrades to suite-level matching (with a warning) rather than
  reporting per-item results.
- **`.importlinter` was not run against a real project.** The generated file is
  verified against import-linter 2.5.2 on a fixture package (contracts evaluate,
  a forbidden import exits 1, an unmapped container would abort the file), but no
  production project's python tree has been linted with it yet.
- **Rego policies are TODO stubs** that deny nothing until implemented.
- Strings are single-line.
- Windows is untested; generated paths use forward slashes.
