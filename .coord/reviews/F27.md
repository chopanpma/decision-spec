# Review F27 — fitness codegen: import-linter contracts

- **Reviewer:** main-orchestrator (independent pass: suite, clippy, real tool)
- **Reviewed at:** commit-less working tree, 2026-10-02 (`.coord/claims/F27.md`)
- **Verdict:** **approve**

## What was asked

The generated `.importlinter` emitted contracts for every rel, including
frontend containers that import-linter cannot import; it should scope contracts to
containers with a `[stack.fitness.packages]` mapping and emit TODOs for the rest.
The no-`root_package` TODO behaviour was explicitly to be kept.

## What was delivered

- A contract pair is emitted only when both endpoints are mapped; otherwise an
  actionable TODO naming each unmapped container and the key to add.
- Contract sections are now `[importlinter:contract:<id>]` — see finding below.
- Direction pinned by test (forbidden source = rel's TO side).
- The `root_package` TODO is retained, and `root_package =` is never emitted empty.

## The bigger bug this surfaced

The generated sections were spelled `[contract:<id>]`. import-linter 2.5.2's INI
reader (`adapters/user_options.py:59-67`) keeps only sections starting with
`importlinter:`. `[contract:…]` is silently ignored: the tool prints
`Contracts: 0 kept, 0 broken.` and exits **0**. So the fitness row has always
been a no-op that reported a pass — worse than the un-runnable config the board
predicted. Fixed and verified (below). This is exactly the task title ("fitness
codegen emits contracts import-linter cannot run") and stayed inside F27's scope
(`crates/codegen` only).

## Verification performed

1. `cargo build && cargo test` → 131 green, clippy `-D warnings` clean.
2. Red-first: HEAD `importlinter()` + new tests → 2 failures; and with only the
   prefix reverted → the same 2 failures. Both red for the right reason.
3. Real tool (import-linter 2.5.2 in a throwaway venv):
   - old prefix + a real violation → `0 kept, 0 broken`, exit 0 (silent pass);
   - landed file + compliant tree → `2 kept, 0 broken`, exit 0;
   - landed file + `auth → api` → `2 broken`, `myapp.auth is not allowed to
     import myapp.api`, exit 1;
   - landed file for a mixed-stack spec (third container unmapped) → the python
     contracts evaluate, the unmapped rel is a TODO, exit 0;
   - hand-written contract naming an unmapped container → `Module 'frontend_app'
     does not exist.`, exit 1 — which confirms the scoping rationale rather than
     assuming it.

## Test reconciliation (AGENTS.md §1)

Two pre-existing tests encoded the old "unmapped → bare container id" behaviour
(`unmapped_containers_fall_back_to_the_container_id`, and the e2e
`contract_e2e_infra_fitness_artifacts` which asserted `type = forbidden` from a
default config). The board task — pilot evidence from a real project — is the
newer authority for the behaviour, so the tests moved rather than the code. No
assertion was weakened: the e2e test still requires live `forbidden` + `layers`
contracts (it now renders with the demo's containers mapped) and the unmapped
case still requires an actionable TODO. Recorded in the claim file.

## Remaining risk (accepted, documented)

- fitness rows remain adapter-status based (`Ran`/`Failed`), so a genuinely
  passing run cannot be distinguished from a skipped linter in the matrix — a
  pre-existing design decision, out of scope here.
- README's "not run against import-linter" bullet was rewritten: the artifacts are
  now executed against the real tool, but never against a production project's
  pinned toolchain.
