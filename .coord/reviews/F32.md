## Findings

- **major** — The specs-only staging restriction is **not pinned by any test**
  (proven by mutation (c): `git add specs` → `git add -A` keeps the whole suite
  green). `create_spec_pr_commits_pushes_then_reports_gh_failure` (main.rs:3079)
  asserts the commit contains exactly `specs/0001-auth.spec`, but its fixture
  dirties only a spec file, so widening the staging scope is invisible — the
  exact regression the flow exists to prevent would land silently, and in
  production a user with dirty non-spec files would PR them. Additionally the
  refusal branch (main.rs:1874-1880: staged-empty → `reset` + `checkout -` +
  `branch -d` → Err "refusing") has **zero coverage** — my scratch probe passes,
  so the behavior is correct today, but nothing pins the worktree restore.
  Fix (small): dirty a non-spec file in the fixture alongside the spec edit
  (then `add -A` stages it and the diff-tree assertion goes red), and add a
  refusal-path test (dirty only `decispec.toml` → Err "refusing" + no
  `spec/tui-*` branch + HEAD restored + edit intact — my scratch test is a
  working template).
- **major** — `create_spec_pr_commits_pushes_then_reports_gh_failure` is
  environment-dependent: **fails on machines without `gh`** (verified with
  `PATH=/usr/bin:/bin` against the real compiled test binary; panics at
  main.rs:3068). Without gh, `pr_readiness` short-circuits before any branch is
  created, so the branch/push/origin-log post-assertions have nothing to stand
  on. The test's own comment claims both environments are acceptable; they are
  not, and `cargo test` must stay green on any box. Fix: inject `gh_ok` into
  `create_spec_pr` the same way `pr_readiness` already takes it (production
  passes `gh_available()`; the test passes `true`, so branch+commit+push run
  everywhere and only the deterministic `gh pr create` failure is asserted).
- **minor** — `app.rs:279-282`: the guard `ed.state.dirty && !was_dirty` means
  an edit made **after** the discard confirmation is armed does **not** cancel
  it, so the next single Esc discards post-prompt edits without re-confirming —
  contradicting the code's own comment ("any real change cancels a pending
  discard confirmation") and USAGE's "`esc` … asks once before discarding".
  Proven by scratch test (`confirm_discard` still set after typing). Fix is
  one line: `if ed.state.dirty { ed.confirm_discard = false; }` (the Esc branch
  returns before this code, so arming is unaffected), plus a regression test.
- **minor** — The armed discard state is invisible: `confirm_discard` is never
  rendered (`views.rs` never reads it; the status bar is untouched on Esc), and
  `editor_shows_text_diagnostics_and_discard_warning` (views.rs:692) is named
  after a warning it never asserts. As shipped, the "ask" in "asks once before
  discarding" shows nothing to the user. Render the armed state (e.g. swap the
  hint line to "esc again to discard changes") and assert it.
- **nit** — Stale read-only claims post-F32: `crates/tui/src/lib.rs:1-10`
  ("read-only", "nothing is ever written into a registered project"),
  `crates/tui/Cargo.toml` description, and README's "The spec cockpit (TUI)"
  paragraph ("strictly read-only … never writes into them") all predate the
  save/PR actions; the README table row was updated but the paragraph wasn't —
  the file now contradicts itself. AGENTS.md makes docs normative.
- **nit** — Status wording on a written-but-broken save: the cli loop formats
  `"save failed: {e}"` while `e` says "saved {file}, but the workspace now
  fails check: …" — the full message reads "save failed: saved …". Call it a
  check failure, not a save failure.
- **nit** — `EditorState::scroll_to_cursor` (editor.rs:167) is dead in
  production: nothing calls it outside tests; `views.rs:491-497` reimplements
  the same clamp inline. One scroll-truth, please (or call the method).
- **nit** — `views.rs:498`: `chunks[0].width as usize - 2` underflows (debug
  panic) when the main pane is < 2 cols wide — reachable by narrowing the
  terminal below the 22-col sidebar. Pathological, but it's a panic in the
  default (dev) build; a `saturating_sub` costs nothing.
- **nit** — Claim arithmetic: "was 170 pre-F32 → +28 tui +6 cli" sums to 204,
  not 202; the real pre-F32 total was 168 (cli 33 + tui 29 + 106 others →
  39 + 57 + 106 = 202 ✓). Same class of bookkeeping nit the F31 review caught.

## Recommendations

- **Land the two test fixes before `done`** (majors 1–2): one fixture line
  (dirty a non-spec file), one new refusal test, and `gh_ok` injection into
  `create_spec_pr`. All three are test-only; no production behavior needs to
  change — the PR flow itself is correct (verified end-to-end against a local
  bare origin, refusal restore probed, push/gh failures named cleanly).
- Fix the `confirm_discard` condition and render the armed state (minors 1–2) —
  this is the editor's only data-loss-adjacent path and today both the code
  comment and the docs overpromise what the UI does.
- Sweep the stale "read-only" doc strings (lib.rs, README paragraph, tui
  package description) as part of this row — README is already in scope.
- Consider deleting `scroll_to_cursor` or calling it from the view; and
  `saturating_sub` in the cursor-x clamp.
- No structural changes recommended, because the Input/Action seam keeps
  proving itself: every mutation above was testable without a terminal, the PR
  flow is fully exercisable against a local bare origin, and cli remains the
  only place that knows about git, gh, or crossterm. The architecture held;
  the test suite around the safety core is what's thin.
