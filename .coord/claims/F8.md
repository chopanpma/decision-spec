# Claim F8 — `specforge extract`

- **Owner:** main-orchestrator
- **Status:** claimed
- **Started:** 2026-10-01

## Task

Add a command that reads an already-started project (Python, JavaScript, or
TypeScript) and extracts a draft spec from it: containers from the directory
layout, relationships from the import graph, plus suggested
`[stack.fitness.packages]` mappings. Output is a DRAFT `.spec` the user edits;
extraction never pretends to recover decisions/requirements.

- Root: `Cargo.toml`, `Cargo.lock` (workspace member), `ARCHITECTURE.md`
  (patterns + MVP gaps), `README.md` (command table + DSL notes),
  `docs/USAGE.md` (extract section)

## Out of scope — must NOT touch

- `.coord/` files other than this claim and my BOARD row
- `AGENTS.md`, `docs/REVIEW.md`

## Review round 1 (2026-10-01) — two MAJOR findings, both fixed TDD-style

### Finding 1: container ids could be invalid DSL ids

`ir::names::sanitize` only maps `-` → `_`, so a directory like `my pages`
rendered `container my pages "my pages"` and the draft failed
`specforge check`. Fix in `crates/extract`: a new `container_id_base` scrubs
any character outside ASCII `[A-Za-z0-9_-]` to `_` **before** the existing
`sanitize` + `_2/_3` collision pass (the pass and its dedupe semantics are
unchanged; `ir::names::sanitize` itself is untouched — it is the shared
test-name registry). Titles keep the raw directory name (quoted + escaped).

**Red evidence (lib):** `cargo test -p specforge-extract` with the new tests
against the un-fixed code: `test result: FAILED. 19 passed; 3 failed` —
- `container_ids_scrub_chars_outside_the_id_charset`: `left: [… id: "my pages" …]`, `right: [… id: "my_pages" …]`
- `scrubbed_id_collisions_still_get_distinct_suffixes`: `left: ["a b", "a_b", "a.b", "a_b_2"]`, `right: ["a_b", "a_b_2", "a_b_3", "a_b_4"]`
- pre-existing `container_ids_sanitize_and_dedupe_with_numeric_suffixes` stayed green throughout (scrub is additive).

### Finding 2: `init` then `extract` analyzed SpecForge's own scaffold

`init` writes `tests/glue/*.py`; on a 2-`.ts` project the glue files tied the
language count and the tie-break flipped the draft to a lone Python `tests`
container. Fix, two halves:
- `crates/extract`: `analyze` now takes `analyze(root, exclude: &[PathBuf])`
  — root-relative dirs/files to skip, matched in `walk` the same way noise
  dirs are (`rel.starts_with(exclusion)`; empty exclusions ignored). All 15
  existing call sites updated to `&[]`; behavior for them unchanged.
- `crates/cli` `cmd_extract`: reads the project config (tolerantly —
  a pre-SpecForge project has no `specforge.toml`, so it falls back to
  `Config::default()`) and passes `tests/generated` unconditionally plus the
  glue package directory (`glue_module` with `.` → `/`, default
  `tests/glue`).

**Red evidence (lib):** same run as above —
`analyze_with_exclusions_skips_scaffold_dirs`: `left: Python`, `right:
TypeScript` (exclusions accepted but not yet applied). 19 pre-existing lib
tests stayed green.

**Red evidence (cli):** `cargo test -p specforge --bin specforge` with
`cmd_extract` passing `&[]`: `test result: FAILED. 15 passed; 2 failed` —
- `extract_ignores_specforge_scaffold_in_python_projects`: panicked at the
  `!text.contains("container tests")` assertion (draft contained
  `container tests "tests"`).
- `extract_ignores_specforge_scaffold_when_detecting_language`: panicked at
  the `container lib "lib"` assertion (draft was the lone flipped

## Review round 2 (2026-10-01) — one MAJOR + one MINOR finding, TDD-fixed

### Finding 1 (major): single-umbrella transparency

Depth-1-only containers collapsed nearly every real project (`src/{pages,
lib}`, `shop/{auth,payments,catalog}`) into one blob container with zero
relationships — the import graph, extract's most valuable output, became
all self-edges. Fix in `crates/extract`: after the depth-1 dir set is
computed (exclusions already applied, so the scaffold `tests/` cannot count
toward the condition), when **exactly one** depth-1 dir `U` has winning
files **and** ≥2 of its child dirs have winning files, `U`'s children are
promoted to containers (title = child name, dir path `U/child`, module
`U.child` python / `U/child` js-ts); files directly under `U` stay in an
`U`-named container; root loose files unchanged; ≥2 depth-1 dirs are
deliberately not promoted. Importer resolution now uses the same
deepest-dir-prefix owner match as js relative imports (`by_path`), so rels
appear automatically; python mapping stays first-segment-vs-title.

**Red evidence (lib):** `cargo test -p specforge-extract` with the new
tests against pre-fix code: `test result: FAILED. 23 passed; 3 failed` —
- `analyze_python_umbrella_project_promotes_children`: `left: [… shop …]`, `right: [auth, catalog, payments, shop]`
- `analyze_ts_umbrella_project_promotes_src_children`: `left: [src]`, `right: [lib, pages, src]`
- the two no-promotion pins (`two_top_level_dirs_with_children_are_not_promoted`, `single_dir_with_only_loose_files_stays_one_container`) passed pre-fix by design — they pin behavior that must survive.
- Note: the round-1 test `analyze_ts_project_with_src_layout_collapses_to_src_container` was **rewritten** as `analyze_ts_umbrella_project_promotes_src_children` — it pinned exactly the collapsed-src behavior this finding abolishes (its node_modules-exclusion assertion is preserved in the new version).

### Finding 2 (minor): python fitness suggestion emitted non-importable names

`root_package = "<project_name>"` and `"<project_name>.<module>"` used the
raw dir name (`my-shop` — legal on disk, not importable). Fix: new
`python_dotted` scrub (`[^A-Za-z0-9_.]` → `_`) applied to `root_package` and
python package values in `render_fitness_toml`; JS/TS values (filesystem
paths) untouched.

**Red evidence (lib):** same run as above —
`fitness_toml_sanitizes_python_package_names`: panicked on
